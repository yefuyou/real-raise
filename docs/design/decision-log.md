# Real Raise 决策日志

> 本文记录产品级决策，不替代 `docs/decisions/` 中的技术 ADR。
> 来源标记为 Repo-observed、User-provided 或 Inferred，避免把当前叙事倒写成历史事实。

## D-01 从“真实购买力”转向“生活余量”

- **来源**：Repo-observed + User-provided
- **背景**：首版以“涨薪还剩多少”“被房租吃掉了吗”“真实购买力”为主。加入工资条、扣缴与支出后，权威结果实际是两期可支配结余差。
- **备选方案**：
  1. 继续做宏观购买力计算器；
  2. 做通用工资/个税计算器；
  3. 聚焦“涨薪后每月真正多留下多少”。
- **最终决策**：选择 3；副标题采用“涨薪后的生活余量”。
- **理由**：与 `monthlyRemainderChange` 一致；更贴近用户决策；避免承诺一个宏观购买力模型。
- **影响**：Hero 需要从抽象“购买力”过渡到明确输入和金额输出；购买力百分比降为辅助指标。
- **重新考虑条件**：如果有稳定用户需求与可核验数据支持跨城市/长期真实购买力指数，再建立独立指标，不覆盖当前结余主线。

## D-02 核心数字不交给模型

- **来源**：Repo-observed
- **背景**：工资、扣缴、支出和结余是强确定性问题；让模型计算会降低可复核性。
- **备选方案**：
  1. 模型直接读原始输入并输出所有数字；
  2. 前端公式计算，模型可自由修正；
  3. 确定性内核冻结数字，模型只解释和做受控 scenario。
- **最终决策**：选择 3。
- **理由**：公式可测试、可对账；供应商变更不影响核心金额；失败时基础产品仍可用。
- **影响**：Worker 必须复算并封存产物；prompt 禁止重算；UI 核心卡不读取模型数字。
- **重新考虑条件**：不重新考虑“模型覆盖核心数字”；只可增加由确定性代码定义、模型不能改写的新指标。

## D-03 增加 Judge Mode

- **来源**：Repo-observed + Historical
- **背景**：比赛评委需要无需个人账号体验真实 Agent，同时项目方必须控制 Secret、额度和并发。
- **备选方案**：
  1. 只展示 Mock；
  2. 浏览器 BYOK；
  3. 服务端项目 Key + 评委短时签名 token；
  4. 只展示 Replay。
- **最终决策**：比赛阶段选择 3，并保留 4 作为降级。
- **理由**：真实调用可验证；Key 不进入浏览器；可做限流与过期。
- **影响**：产生 Judge session、rate limiter、项目额度和额外 UI/文档；当前 UI 已移除 Judge，Worker 代码仍在，生产 health 显示未配置。
- **重新考虑条件**：只有再次出现明确的受控评审场景；否则继续清理为历史兼容，不恢复普通用户入口。

## D-04 一度推进 Partner SSO

- **来源**：Repo-observed + User-provided
- **背景**：比赛关注真实用户数，运营建议登录/注册；同时希望 live 任务消耗用户个人额度并正确归因。
- **备选方案**：
  1. 匿名项目额度；
  2. Judge-only；
  3. Partner SSO + 服务端用户 API Key；
  4. 只保留 Replay。
- **最终决策**：实现 3，同时匿名用户保留基础算表与 Replay。
- **理由**：解决用户归因与额度边界；避免浏览器 BYOK。
- **影响**：实现 state、Cookie、callback、logout、localhost handoff、Durable Object session 与用户级 usage scope；复杂度显著提高。
- **重新考虑条件**：当前只维护安全与可用性，不继续扩展账号系统。若真实用户研究证明登录能提升核心任务完成率，再重新评估。

## D-05 冻结登录扩展、排行榜和用户系统

- **来源**：User-provided，2026-07-28
- **背景**：MVP、Demo、Judge、公开传播已完成；继续做注册、排行榜和历史记录主要服务比赛用户数。
- **备选方案**：
  1. 继续追比赛指标；
  2. 完全删除已完成 SSO；
  3. 冻结扩展，保留已实现链路，转向可信收尾。
- **最终决策**：选择 3。
- **理由**：边际收益低；当前缺口是接管、证据与产品故事；立即删除会扩大本轮范围并丢失历史。
- **影响**：SSO 被归类为“已实现的平台尝试”，而不是未来产品路线；排行榜、历史、更多城市、PWA、开放 API 默认 P2。
- **重新考虑条件**：有带原文、场景、频次的真实反馈，并能说明为何不破坏核心数字可信度。

## D-06 不建立第二套 Landing Page

- **来源**：User-provided
- **背景**：为了比赛、简历或宣传另做一套静态首页，会形成第二个产品叙事与第二组截图。
- **备选方案**：
  1. 单独建 Portfolio landing；
  2. 在现有产品与 README 上整理证据；
  3. 用外部作品集只链接仓库与 Demo。
- **最终决策**：当前选择 2，必要时外部作品集采用 3。
- **理由**：减少事实漂移；README 与真实 UI 必须共用同一套产品价值；时间优先投入测试、Release 和复盘。
- **影响**：现有 README 的截图、能力表和部署说明必须随代码核验。
- **重新考虑条件**：核心仓库已经完成 Release，外部作品集需要统一展示多个项目时，可做只读索引，不复制技术声明。

## D-07 当前优先 CI、Release 与技术接管

- **来源**：User-provided + Repo-observed
- **背景**：仓库已经有 CI，但测试存在误导性总结；生产部署不带 commit；没有 Release；任务恢复等声明超出实现。
- **备选方案**：
  1. 继续开发功能；
  2. 只美化 README；
  3. 先建立事实审计、固定输入回归、故障注入、部署证据和 Release。
- **最终决策**：选择 3。
- **理由**：它直接决定简历和面试陈述能否承担技术真实性责任。
- **影响**：本轮新增事实审计、请求生命周期、三输入出口脚本、复盘与决策日志；不部署生产。
- **重新考虑条件**：P0 可信收尾完成并形成第一个可追溯 Release。

## D-08 Real Raise 是当前唯一主线

- **来源**：User-provided
- **背景**：多个 Agent、worktree、分支和历史部署造成“哪个版本才是产品”的持续成本。
- **备选方案**：
  1. 并行维护比赛版、Partner 版、Portfolio 版；
  2. 另起新仓库重写；
  3. 以 Real Raise 当前仓库为唯一主线，历史方案归档。
- **最终决策**：选择 3。
- **理由**：现有仓库已经包含完整演进证据；重写会丢失真实教训；多主线会继续制造 README/生产漂移。
- **影响**：新工作必须从 `origin/main` 和最新 truth audit 开始；独立分支通过 Draft PR 合流；未知价值文件先归档不删除。
- **重新考虑条件**：只有安全、许可证或技术平台约束证明无法在原仓库演进时，才考虑迁移，并保留完整 provenance。

## D-09 Agent 产出与个人贡献分开陈述

- **来源**：Repo-observed + User-provided
- **背景**：Git author 多数统一显示仓库所有者；归档交接明确哈吉米/Antigravity 偏前端执行，Codex 负责审计、修复、测试、CI、脚本和文档。仅凭 Git author 无法细分逐行作者。
- **备选方案**：
  1. 把所有代码包装成个人手写；
  2. 把所有成果归给 Agent；
  3. 按“产品决策、Agent 实现、人工验收、当前证据”四层陈述。
- **最终决策**：选择 3。
- **理由**：既不贬低 AI 协作，也不夸大个人编码贡献。
- **影响**：Portfolio 应重点证明问题定义、范围收敛、Agent 指挥、上线推进、审计判断和停止低 ROI 功能；具体实现贡献只在有 commit/交接证据时归因。
- **重新考虑条件**：获得更细的任务记录或作者 attestation 后，可补充模块级贡献表，不回写无法证明的逐行归属。
