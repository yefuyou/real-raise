## 结论

反复返工的主因不是单个组件难，而是缺少四种项目控制：

1. 没有唯一产品状态机。
2. 没有区分目标、仓库、分支和生产状态。
3. 重大决定没有 ADR，旧方案持续留在文档根目录。
4. 多任务并行时缺少 checkpoint 和工作树所有权。

## Git 与发布流程的返工

### PR base 错位

PR #6 合入 `codex/partner-sso`，而不是直接进入 `main`。GitHub 显示 merged，但主分支当时没有得到预期的数据链。这说明“PR 已合并”不能替代目标分支检查。

控制措施：

- Checkpoint 同时记录 base、head、merge commit 和 `origin/main`。
- 合并前检查 `git log origin/main..HEAD` 与 PR base。

### Checkpoint PR 被合并

PR #7 最初被描述为保存当前版本、不可直接合并，随后于 2026-07-30 01:01 被外部操作合入 `main`。这不是代码错误，而是发布语义没有被工具状态强制表达。

控制措施：

- Draft/不可合并状态必须在 PR 标题、body、标签和分支保护中同时体现。
- “checkpoint”不能依赖口头约定。
- Changelog 记录实际合并，但不得推导生产已部署。

- `CRITICAL_DATA_CHAIN_RELEASE.md` 写生产 NO-GO，但相关 PR 后来已合并，生产状态又没有对应 Checkpoint。
- `INFINISYNAPSE_MODEL_SELECTION.md` 标为历史后，产品模型选择也被误删，说明文档分类影响了实现判断。

## 新的完成定义

一个改动只有同时满足以下条件才算完成：

1. 产品规格或 ADR 说明为什么做。
2. 状态机覆盖新增或改变的状态。
3. 代码与测试实现。
4. Changelog 记录实际变化。
5. Checkpoint 记录 commit 和验证证据。
6. 若部署，Runbook 和生产证据完成。

缺任何一项，都只能称为“代码已写”“PR 已合”或“生产可访问”中的一种，不能笼统称为“完成”。
