# Real Raise 2026 年 7 月项目总复盘

> 主题：一个生活问题如何成为上线产品，又如何从快速 AI 开发造成的事实漂移中被重新接管。
> 证据基线：`origin/main` @ `d25bb6b`。
> 相关事实：[仓库事实审计](../engineering/repository-truth-audit.md)、[产品旅程](../product/product-journey.md)、[请求生命周期](../engineering/request-lifecycle.md)。

## 1. 这不是“项目成功/失败”的二选一

Real Raise 已经完成了许多黑客松项目没有完成的事：从真实问题出发、形成 MVP、做成可操作页面、上线公网、接入真实平台能力、公开发布视频，并在方向收益下降时主动停下。

它也暴露了 AI 协作开发最典型的接管问题：代码增长快于系统理解，多个 Agent 在不同分支和 worktree 推进，旧总结比代码传播得更快；页面能跑、PR 有绿勾、README 很完整，却仍可能缺少任务恢复、部署身份和可信测试输出。

这次复盘不试图证明项目完美。它要证明项目所有者开始能区分：

> 能运行，是一次演示结果；可信交付，是对公式、状态、身份、失败与证据承担责任。

## 2. 项目起因与用户问题变化

起点是一个有共鸣的生活问题：

> 为什么工资涨了，我还是感觉越来越穷？

首版把它表达为“真实购买力”和“涨薪是否被房租吃掉”。这足以快速形成 MVP：两期到手收入、房租、日常支出与最终结余。

工资条模式加入后，产品问题发生了实质变化。用户不只想知道 CPI 是否跑赢涨幅，而是想看一条可核对的个人账本：

```text
税前工资变化
→ 扣缴变化
→ 到手变化
→ 住房与日常支出变化
→ 每月真正多留下多少钱
```

因此，当前更准确的定位不是“普通工资计算器”，也不是宏观“真实购买力指数”，而是：

> 一个把名义涨薪转换成生活成本变化和可支配结余变化的真实收入诊断工具。

“涨薪后的生活余量”是更贴近代码与用户的副标题。它对应权威结果 `monthlyRemainderChange`，而不是让辅助百分比承担全部叙事。

## 3. MVP 范围：做对了什么

MVP 的关键收敛是把问题限制在“一次涨薪前后”：

- 两期收入，而不是长期财富管理；
- 住房与日常生活支出，而不是完整记账；
- 官方价格基准只作参照，不替代个人房租；
- 结果是月/年结余、保本收入和变化路径；
- 不提供投资、借贷、辞职建议。

这让项目在 2026-07-26 首日就形成了可运行产品。公开部署和视频发布把它从 PRD 推到了真实外部环境。即使播放量很低，发布本身仍是能力证据：它要求完成构建、部署、截图、录屏、文案和外部可访问性。

## 4. AI 与确定性计算边界

项目最值得保留的架构判断是：

> 确定性公式负责数字，Agent 负责解释。

当前代码已经落实了大部分边界：

- 页面用 TypeScript 公式即时计算。
- Worker 不信任客户端 calculation，会重新计算。
- Agent prompt 读取版本化上下文，禁止重算。
- 正式 CSV/Manifest 由 Worker 数字封存。
- 供应商同名数字文件另存为 `vendor-original-*`。
- UI 核心金额不从模型正文反向写入。

但“核心数字只有一个计算源”还没有完全实现。前端和 Worker 各有一份相同公式；浏览器和 Worker 也各有一套产物构造器。本轮三输入 contract test 证明它们现在一致，却也证明必须靠额外审计防止漂移。

更诚实的当前表述是：

> 核心数字有一个业务口径、两个实现位置；live 以 Worker 复算为服务端权威，页面以本地结果即时展示。

## 5. 多 Agent 开发：速度优势

归档文件把分工写得很明确：

- 哈吉米/Antigravity 偏前端体验和重复性执行；
- Codex 偏代码审计、修复、测试、CI、脚本和文档；
- 项目所有者负责问题选择、范围、产品方向、上线与是否继续投入。

这种协作带来的速度是真实的：

1. 四天内从 MVP 推进到工资条、Replay、Worker、SSO、Agent ACT 与文档治理。
2. 前端、数据、后端、部署和宣传材料可以并行产生。
3. Agent 能快速把安全边界、测试矩阵和历史资料写成显性文件。

不应因为后续有返工，就否定这种杠杆。没有 AI 协作，项目大概率不会在如此短时间内走完上线和公开发布。

## 6. 多 Agent 开发：为什么也造成事实漂移

速度的代价主要来自方法，而不只是某一行代码：

### 6.1 分支与工作树不是共享记忆

PR #6 合并到 Partner 分支而非 main；PR #7 名为 checkpoint，最终仍被合并。多个 worktree 中存在不同未提交状态。Agent 看见的“当前项目”可能不是用户以为的主线。

### 6.2 文档把目标、旧路径和生产混在一起

Node server 有 cache 和 task GET；Cloudflare Worker 没有。README 却曾写成“AI live 有缓存”。Judge 曾配置为 true，本轮 health 已是 false；旧 Checkpoint 如果不带时间戳就会变成错误的“现在”。

### 6.3 重复实现提高了局部产出速度

前端、Worker、Replay、CSV 都需要数字，最快的做法是分别复制逻辑。短期能交付，长期必须证明一致。当前三输入通过，不代表设计风险消失。

### 6.4 测试数量取代了测试含义

PR 文案从 33/33 增长到 46，当前实际是 45 个 runner case。本轮 `npm test` 的失败更直接：最后打印 ALL PASSED，但退出码是 1；“任务恢复”测试根本没有走真实生产代码。

教训不是“Agent 不可靠”，而是：

> Agent 生成的实现、测试和总结都只是候选证据，必须由退出码、行为路径、部署身份和人工解释形成闭环。

## 7. 上线与传播

项目当前有可访问的 Cloudflare Demo 和一个公开 B 站视频。B 站快照只有 16 播放、零公开互动。这组数据可以证明发布，不能证明产品验证。

微博、抖音、作品长廊和第一批反馈在用户叙事中存在，但仓库没有帖子 URL、指标快照或反馈原文。复盘必须把它们标为 Unverified，而不是用传播脚本代替发布证据。

传播表达也偏技术抽象。公开视频标题“计算真实涨薪对购买力提升的计算器”没有在五秒内给出具体冲突。更适合的钩子是：

> 税前涨 1000，为什么每月最后只多留下 266？

它先给可感知的差值，再让产品解释去向。

## 8. 比赛指标带来的方向偏移

Judge Mode 的出现有合理背景：评委要体验真实 Agent，项目方又不能暴露 Key。它推动了服务端 Secret、短时 token、额度和降级设计，是有工程价值的比赛能力。

Partner SSO 也不是“无意义功能”。它解决了：

- 用户身份；
- 个人额度；
- Partner user key 服务端保存；
- 平台任务归因；
- 项目额度不被匿名流量消耗。

问题在于目标函数变了。登录、注册、排行榜优化的是比赛用户数，不是“用户能否看懂生活余量”。如果继续做，产品会从一个清晰的单次诊断工具变成平台功能容器。

## 9. 为什么从 Hackathon 转为 Portfolio

2026-07-28 的停止决策是成熟度证据，而不是退缩：

- 已经证明能从 0 到 1。
- 继续堆功能的边际收益下降。
- 真正短板转为接管、验证、解释和维护。
- 一份可信的 case study 比一个未验证排行榜更有长期价值。

因此，当前选择是保留 SSO 作为已实现的历史/平台尝试，冻结其扩展；把优先级转向 CI 真实性、固定输入、故障注入、部署 identity、Release、反馈档案与复盘。

## 10. 工程审计发现的问题

### 已经修复或显著缓解

- **Historical → Observed fixed**：浏览器 BYOK 已退出产品入口；Partner user key 留在 Worker session。
- **Historical → Observed fixed**：Mock 不会从当前 UI 或 live 失败路径自动冒充真实 Agent。
- **Historical → Observed fixed**：Worker 会复算核心生活结余，拒绝伪造 calculation/城市上下文。
- **Historical → Observed fixed**：Replay 已有 v2 双请求、旧口径警告与供应商原件 hash。
- **Historical → Observed fixed**：仓库已有 GitHub Actions，并在 main 最新 commit 通过。
- **Historical → Observed fixed**：lockfile 已使用 npm 官方 registry。

### 当前仍存在

- 前端/Worker 公式重复。
- Worker/browser 产物 contract 6/7 项不一致。
- refresh 后 task 与下载产物丢失。
- 同 Task 追问没有生产闭环。
- live Worker 无结果 cache，README 曾混写 Node 能力。
- 新任务先清空旧报告，失败回退差。
- 测试 runner 会在失败后打印 ALL PASSED。
- 跨平台源码字符串断言在 CRLF 下失败。
- “localStorage 恢复”用例没有测生产行为。
- 生产 deployment 没有 commit identity，审计过程中发生四次无说明部署。
- Worker 不复算 payslip summary。
- Usage lease 4 分钟短于 10 分钟任务超时。

### 尚未验证

- 本轮生产新 OAuth 流程。
- Partner user key 的真实供应商归因。
- 当前 Prompt 的新 live Agent 结果。
- 微博/抖音发布与用户反馈。
- 线上最新 bundle 对应哪个 Git commit。

## 11. 哪些问题来自方法，哪些来自实现

| 类型 | 具体问题 | 根因 |
| --- | --- | --- |
| 方法 | PR 数字被当成当前测试事实 | 没有把 commit、命令、退出码绑定 |
| 方法 | production 与 main 混称 | 部署没有 commit tag/Release |
| 方法 | Agent 生成等于“我掌握了” | 缺少人工从输入到产物的路径解释 |
| 方法 | 多 worktree 状态错位 | 开工前未统一 base、dirty state 与目标分支 |
| 实现 | refresh 无恢复 | live task 只在请求 Response/内存 Map 中 |
| 实现 | duplicate formula | 前端 TS 与 Worker MJS 分别实现 |
| 实现 | false ALL PASSED banner | runner 无 failure count 分支 |
| 实现 | 自动 Replay 降级不够显式 | 模式选择在 API client 内完成 |
| 实现 | artifact contract 不一致 | 两套 manifest builder 独立演进 |

方法问题会反复制造新的实现问题，因此优先级不能只放在补一个函数。

## 12. 做对了什么

1. 从一个真实生活问题切入，而不是先找技术展示场景。
2. 把 MVP 收敛为两期收入与生活结余，而不是做完整财务平台。
3. 坚持“AI 只解释、不改数”，并最终落实到 Worker 复算和产物封存。
4. 真正上线并公开发布，经历外部可访问环境。
5. 在 BYOK 风险暴露后转向服务端 Secret 与 Partner session。
6. 在比赛功能 ROI 下降后主动冻结，而不是沉没成本式扩张。
7. 愿意审计自己已经写进 README 的技术声明，并接受结果不全绿。

## 13. 做错了什么

1. 开发速度超过理解速度，直到后期才系统追请求生命周期。
2. 把 Agent/PR 的“测试全绿”总结当成证据，没有始终检查退出码与断言含义。
3. 让产品、备用后端和生产 Worker 的能力同时出现在 README。
4. 没有在每次部署记录 commit，导致线上可访问却不可归因。
5. 没有及时归档原始反馈、帖子和比赛指标，传播闭环只能靠记忆。
6. 把“真实购买力”放在首屏太久，弱化了真正的月结余价值。
7. SSO 等复杂能力上线前，没有先回答它与核心用户价值的关系。

| 能力 | 证据 |
| --- | --- |
| 从真实问题形成产品 | 初始 MVP 与持续定位收敛 |
| 收敛 MVP | 两期工资/支出/结余的清晰边界 |
| 指挥多个 Agent | 哈吉米/Codex 交接文件、多个并行模块 |

人工判断主要体现在：选问题、定边界、决定上线、接受公开发布、评估比赛 ROI、冻结低价值功能，以及发起本轮严肃接管。

## 15. 尚未完全证明的能力

1. 在一台满足 Node 22 的全新机器上独立从 clone 跑完全部命令。
2. 不依赖旧会话，现场解释 Worker SSO、usage lease、SSE 与 artifact sealing。
3. 修复并亲自维护核心 contract test，而不只运行 Agent 生成脚本。
4. 制造 live Worker/供应商故障并从日志定位根因。
5. 设计持久任务恢复、幂等与用户隔离。
6. 建立 commit → CI → deployment → Release 的发布链。
7. 对生产 Partner attribution 做一次可复核的端到端验证。
8. 为简历每一条技术声明提供对应 commit、测试或运行证据。

这些不是对项目的否定，而是接下来作品化最有价值的学习清单。

## 16. Lessons Learned

### 产品层

1. “购买力”不是越专业越好。初始代码一直在算月结余，直到工资条加入后才更明显；产品名词必须追随权威输出。
2. Judge/SSO 可以是合理工程功能，却不一定是核心产品。它们解决评审与平台指标，不直接改善匿名用户的算表结果。
3. 主动停止也是产品能力。2026-07-28 冻结排行榜等功能，比继续增加页面更能保护单一价值主张。

### 工程层

1. 一个公式被复制到两个运行时，就必须有跨实现 contract test。本轮三输入通过只是建立了防线，不是消除了设计债。
2. 服务能力必须按部署路径描述。Node 有 cache/GET，不代表 Worker 生产有；README 不能用“后端”一词抹平差异。
3. 测试结论必须读取退出码和 failure 行。本轮 44 pass + 1 fail 后仍打印 ALL PASSED，是最具体的反例。
4. 可访问 URL 不是 Release。审计期间四次无 message 部署且 bundle 漂移，证明没有 commit identity 就不能接管。

### AI 协作层

1. Agent 擅长并行产出，但不会自动共享 worktree 事实。PR #6 base 错位说明每个任务都要声明 base/branch/dirty state。
2. Agent 生成的测试可能验证“字符串存在”而非真实行为。任务恢复假测试说明验收必须追到生产代码。
3. 让 Agent 写总结之前，要先固定证据表：commit、命令、退出码、URL、时间戳、未验证项。
4. 贡献应按决策、实现、验收拆开。Git author 统一不能证明逐行作者，诚实归因比包装“全栈手写”更有价值。

### 传播层

1. “计算真实涨薪对购买力提升的计算器”信息很多，却没有一个立即可感知的结果；数字冲突比技术名词更适合前五秒。
2. 发布脚本不是发布证据。微博/抖音没有 URL 和快照，就不能进入 Portfolio 成果数字。
3. 16 次播放证明内容公开，不证明需求成立。小数据应该推动钩子与渠道复盘，而不是被包装成用户验证。
4. 反馈如果不存原文，就会从研究变成传说。现有两个“用户反馈”问题只能保留为待补证据。

### 个人成长层

1. 从“我让 Agent 做出来了”到“我能解释每个请求节点”，是这次项目真正的能力升级。
2. 能够接受 `npm test` 不全绿并把它写进复盘，比追求漂亮状态更接近技术 ownership。
3. 停止低 ROI 功能说明开始用产品目标管理工程，而不是用 feature count 管理成就感。
4. 下一阶段最重要的不是多写代码，而是能在没有旧聊天记录时重建系统真相。

## 18. 项目达到“完成”的验收标准

Real Raise 可以从 Portfolio 角度宣布完成，当且仅当：

1. Node 22 干净环境所有必需命令退出 0，测试不会误报。
